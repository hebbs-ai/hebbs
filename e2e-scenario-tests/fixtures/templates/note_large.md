## Storage Engine Fundamentals

The storage engine sits at the bottom of the architecture stack and is responsible for durable persistence of all memory records. It must guarantee crash consistency, meaning that if the process is terminated at any point between two operations, the data on disk remains in a valid and recoverable state. This requirement shapes every design decision in the storage layer, from the choice of write-ahead logging to the compaction strategy.

The engine uses a log-structured merge tree as its primary data structure. Incoming writes are first appended to an in-memory buffer called the memtable. When the memtable reaches its configured size threshold (default 64 MB), it is frozen and flushed to disk as a sorted string table. The flush operation is atomic: either the entire table is written successfully, or no changes are persisted. This atomicity is achieved through a combination of write-ahead logging and filesystem rename operations.

Sorted string tables on disk are organized into levels. Level 0 contains the most recently flushed tables, which may have overlapping key ranges. Levels 1 through 6 are sorted and non-overlapping within each level. A background compaction process merges tables from one level into the next, resolving overlaps and reclaiming space from deleted or overwritten entries. The compaction strategy uses a leveled approach with a size ratio of 10 between adjacent levels.

Read operations check the memtable first, then proceed through the levels from newest to oldest. Bloom filters attached to each sorted string table allow the engine to skip tables that definitely do not contain the requested key. The false positive rate is configured at 1%, which means approximately one in a hundred lookups will read a table unnecessarily. This trade-off between memory usage (for the bloom filter) and read amplification is tunable per deployment.

The write-ahead log ensures durability before a write is acknowledged. Each write operation appends a record to the WAL, which is synced to disk using fdatasync. The sync interval is configurable: the default is to sync after every write (maximum durability, higher latency), but deployments that can tolerate a small window of potential data loss can batch syncs at 10-millisecond intervals. The WAL is truncated after each successful memtable flush, bounding its maximum size to the memtable size plus a small overhead for in-flight writes.

Point lookups achieve single-digit millisecond latency at the p99 level for datasets up to 10 million records. Range scans are bounded by the number of results requested and the number of levels that must be merged. The engine exposes detailed metrics for read amplification (number of tables consulted per read), write amplification (bytes written to disk divided by bytes written by the application), and space amplification (total disk usage divided by logical data size). These metrics are essential for capacity planning and performance tuning.

Backup and restore operations are built on top of the storage engine's snapshot capability. A snapshot captures a consistent point-in-time view of all data by recording the current set of sorted string tables and the memtable contents. The snapshot is logically immutable: subsequent writes do not modify the snapshot's view, because they create new tables rather than modifying existing ones. This copy-on-write property means snapshots are nearly free to create (the cost is proportional to the metadata size, not the data size), making them suitable for frequent automated backups.

The storage engine's compaction filter mechanism provides a hook for tenant-specific data lifecycle policies. During compaction, each record passes through a configurable filter chain that can inspect the record's key, value, and metadata. Filters can decide to keep the record, drop it, or transform it. Common uses include TTL enforcement (dropping records older than a configured threshold), data masking (redacting sensitive fields for compliance), and format migration (transforming records from an old schema to a new one). Filters execute synchronously during compaction, so they must be fast; a slow filter degrades compaction throughput and can cause write stalls.

The engine's memory allocator is tuned for the specific allocation patterns of LSM-tree workloads. Memtable construction involves many small allocations (one per key-value pair) followed by a single large deallocation (when the memtable is flushed and freed). The engine uses an arena allocator for memtable entries, which allocates from a contiguous memory region and frees everything at once when the memtable is discarded. This eliminates per-entry deallocation overhead and reduces memory fragmentation compared to the general-purpose allocator.

## Vector Index Architecture

The vector index enables similarity search over high-dimensional embedding spaces. Each memory record is associated with one or more embedding vectors, typically generated by a neural language model. The index must support approximate nearest neighbor queries with configurable recall targets, allowing operators to trade query speed for result quality based on their application requirements.

The index implementation uses a hierarchical navigable small world graph. This data structure organizes vectors into a multi-layer graph where each layer is a navigable small world network. The top layers contain a sparse subset of all vectors and enable fast coarse-grained navigation. The bottom layer contains all vectors and provides fine-grained search. A query starts at the top layer and greedily descends, using each layer's nearest neighbor as the entry point for the layer below.

Construction of the graph proceeds incrementally. When a new vector is inserted, the algorithm randomly assigns it a maximum layer using an exponentially decaying probability distribution. The vector is then connected to its nearest neighbors in each layer from the top down to layer zero. The number of connections per node is bounded by a parameter M (default 16 for layer zero, M/2 for higher layers). This bound is critical for controlling memory usage and query latency, as each connection requires storing a node identifier and contributes to the search frontier during queries.

The search algorithm maintains a priority queue of candidate nodes, ordered by distance to the query vector. At each step, it expands the closest unexplored candidate by examining all of its neighbors. Neighbors that are closer to the query than the current worst result are added to both the candidate queue and the result set. The search terminates when no unexplored candidate is closer than the worst result, or when a configurable exploration factor (ef_search) limits the number of candidates examined.

Distance computation dominates query latency. For 768-dimensional float32 vectors, a single distance computation requires 768 multiply-accumulate operations. The engine uses SIMD instructions (AVX-512 on x86, NEON on ARM) to parallelize these operations across vector lanes. With AVX-512, sixteen float32 operations execute per cycle, reducing a 768-dimensional distance computation to approximately 48 cycles plus overhead. Quantization to int8 further reduces this by a factor of four at the cost of approximately 2% recall degradation.

The index supports filtering during search, allowing queries to restrict results to memories matching specific criteria (time range, source, kind). Filters are applied during graph traversal rather than as a post-processing step. This pre-filtering approach avoids the recall degradation that post-filtering causes when the filter is highly selective. However, pre-filtering can slow down traversal when the filter eliminates many candidate nodes, requiring the search to explore more of the graph. The engine uses an adaptive strategy that switches between pre-filtering and post-filtering based on estimated filter selectivity.

Memory usage for the index scales linearly with the number of vectors and the dimensionality. For 768-dimensional float32 vectors with M=16 connections, each vector requires approximately 3.2 KB of memory (3072 bytes for the vector itself, plus approximately 128 bytes for graph connectivity metadata). A deployment with one million memories therefore requires approximately 3.2 GB of memory for the vector index alone, not counting the storage engine's memory requirements.

Index maintenance operations run continuously in the background to keep the graph in optimal shape. Over time, insertions and deletions can degrade graph quality by creating suboptimal connections. The maintenance process identifies nodes with poor connectivity (measured by the average distance to their neighbors relative to the ideal nearest neighbors) and reconnects them to better candidates. This maintenance is similar to the optimization phase in offline graph construction algorithms, but it operates incrementally on a live index without blocking queries.

The vector index supports multiple distance metrics: cosine similarity, euclidean distance, inner product, and hamming distance (for binary vectors). The metric is selected at index creation time and cannot be changed without rebuilding the index. Cosine similarity is the default for text embeddings because most language models are trained with a cosine objective. Euclidean distance is preferred for geometric embeddings (coordinates, positions). Inner product is used when the vector magnitude carries semantic meaning (relevance scores, confidence weights).

Persistence of the HNSW graph uses a custom binary format optimized for memory-mapped access. The graph is serialized as a sequence of node records, each containing the node's vector, layer assignment, and neighbor lists. The format is designed for zero-copy deserialization: the graph can be loaded by memory-mapping the file and interpreting the bytes directly as node structures, without copying data into heap-allocated objects. This reduces startup time from minutes (for large graphs that require deserialization) to seconds (for memory mapping) and allows the operating system's page cache to manage memory pressure automatically.

## Query Processing Pipeline

The query processing pipeline transforms a user's natural language query into a ranked list of relevant memories. The pipeline consists of five stages: query analysis, embedding generation, candidate retrieval, re-ranking, and response assembly. Each stage has a latency budget, and the sum of all budgets must not exceed the end-to-end latency target of 100 milliseconds at p99.

Query analysis examines the input text to extract structured intent signals. These signals include temporal references ("last week", "in January"), entity mentions (people, projects, systems), and semantic qualifiers ("important", "related to", "contradicts"). The analysis uses a lightweight rule-based parser for temporal and entity extraction, reserving neural models for semantic understanding. The rule-based parser operates in under 1 millisecond, while neural analysis is deferred to an optional enrichment step that runs in parallel with embedding generation.

Embedding generation converts the query text into a vector representation compatible with the vector index. The engine supports multiple embedding models, selectable per tenant. The default model produces 768-dimensional float32 vectors and runs in approximately 5 milliseconds on a modern CPU (no GPU required). For deployments with GPU access, batch embedding of multiple queries can achieve sub-millisecond per-query latency through hardware parallelism. The embedding model is loaded into memory at startup and shared across all query threads.

Candidate retrieval uses the vector index to find the k most similar memories to the query embedding. The default k is 100, which provides a large enough candidate pool for the re-ranking stage to produce high-quality final results. The retrieval stage also applies any pre-filters extracted during query analysis, such as time range restrictions or source filters. This stage targets a latency budget of 10 milliseconds, which is achievable for datasets up to 10 million memories with the HNSW index configured at ef_search=128.

Re-ranking applies a more expensive scoring model to the candidate set to improve result quality. The re-ranker considers factors beyond vector similarity: recency (newer memories score higher, with configurable decay), source authority (memories from curated sources score higher than raw ingestion), link density (memories referenced by many other memories score higher), and explicit importance signals (user-assigned or engine-inferred importance scores). The re-ranker uses a learned-to-rank model that combines these signals with weights tuned on relevance judgments. It processes the 100-candidate set in approximately 15 milliseconds.

Response assembly formats the final ranked list for the client. It retrieves the full content of the top results from the storage engine, applies any content transformations (snippet extraction, highlight marking), and constructs the response payload. Snippet extraction identifies the most relevant paragraph within each memory by computing paragraph-level similarity to the query. This avoids returning entire long documents when only a small section is relevant. The assembly stage targets a latency budget of 20 milliseconds, which includes storage reads for up to 20 full memory records.

The query processing pipeline also supports federated queries that span multiple engine instances. When a query is sent to an instance that is part of a cluster, the instance can optionally fan out the query to all other instances, merge the results, and return a unified ranked list. The fan-out is performed in parallel, with the total latency bounded by the slowest instance plus the merge overhead. The merge operation uses a k-way merge of pre-sorted result lists, which runs in O(k * log(n)) time where k is the total number of results across all instances and n is the number of instances.

Query caching reduces latency for repeated queries by storing recent query results in an LRU cache keyed by the query embedding hash and filter parameters. Cache entries are invalidated when any memory that appeared in the cached results is modified or deleted. The invalidation mechanism uses the storage engine's change notification system to identify affected cache entries efficiently. Cache hit rates typically range from 15% to 40% depending on the query workload's repetitiveness. The cache size is configurable and defaults to 1000 entries per tenant.

The pipeline supports query explanations that provide visibility into why specific memories were ranked in their positions. When the explain flag is set on a query, the response includes per-result explanations showing the vector similarity score, the re-ranking score breakdown (recency contribution, authority contribution, link density contribution, importance contribution), and any boost or penalty factors applied by the ranking model. Explanations are invaluable for debugging relevance issues and tuning the re-ranking model weights.

## Consistency and Replication

Consistency guarantees determine how the system behaves when memories are written and read concurrently. The engine provides read-after-write consistency within a single process: any memory written by a client is immediately visible to subsequent reads from the same client. This guarantee holds even if the memory has not yet been flushed from the memtable to disk, because reads check the memtable before consulting on-disk tables.

Cross-process consistency is more nuanced. When multiple engine instances share a storage backend (for example, in a distributed deployment), a write to one instance is not immediately visible to reads from another instance. The engine uses an event-based replication protocol to propagate changes between instances. Each write generates a change event containing the memory identifier, the new content hash, and a vector clock timestamp. Change events are published to a shared event log and consumed by all instances.

The replication protocol provides eventual consistency with bounded staleness. Under normal operation, a write to one instance becomes visible to all other instances within the replication lag, which is typically under 100 milliseconds for co-located instances and under 500 milliseconds for geographically distributed deployments. The staleness bound is configurable, and the engine exposes a metric tracking the current replication lag per instance.

Conflict resolution uses a last-writer-wins strategy based on vector clock timestamps. When two instances concurrently modify the same memory, the modification with the higher vector clock value takes precedence. In the rare case of identical vector clock values (which requires perfectly simultaneous writes to different instances), the engine falls back to a deterministic tie-breaking rule based on the instance identifier. This ensures that all instances converge to the same state regardless of the order in which they process change events.

The vector index presents additional replication challenges. Unlike the storage engine, which can replay individual write operations, the HNSW graph requires careful handling of concurrent inserts and deletes. The replication protocol batches graph mutations and applies them atomically using a read-copy-update mechanism. This ensures that queries always see a consistent snapshot of the graph, even while updates are being applied. The RCU mechanism introduces a brief period (typically under 5 milliseconds) during which two versions of the graph coexist in memory, doubling the index memory footprint momentarily.

Durability guarantees are tied to the write-ahead log configuration. In the default configuration (sync after every write), a write is durable as soon as it is acknowledged. In batched sync mode, writes are durable after the next sync boundary (at most 10 milliseconds). The replication protocol does not add additional durability guarantees beyond what the local WAL provides. If an instance fails before replicating a write, the write may be lost if it was not yet synced to the local WAL. Operators who require stronger durability guarantees can configure synchronous replication, which waits for at least one replica to acknowledge the write before responding to the client.

Consistency verification runs as a periodic background task that detects and repairs divergence between replicas. The verifier computes Merkle tree hashes over key ranges for each instance and compares them across the cluster. Divergent ranges are identified by walking the Merkle tree from root to leaves, narrowing down to the specific keys that differ. Once divergent keys are identified, the verifier applies the conflict resolution strategy (last-writer-wins by default) to bring all replicas into agreement. The verification process is rate-limited to avoid consuming excessive network bandwidth and is designed to complete a full scan of the dataset within 24 hours for deployments up to 10 million memories.

The replication protocol handles schema evolution gracefully. When a new version of the engine introduces changes to the memory record format, the change events include both the old and new format representations during a configurable transition period. Older instances that have not yet been upgraded can continue processing events using the old format, while upgraded instances use the new format. This dual-format approach allows rolling upgrades across a cluster without downtime or data loss. After all instances have been upgraded, the old format representations are dropped from subsequent events.

## Memory Lifecycle Management

Memories in the system have a well-defined lifecycle that governs their creation, evolution, and eventual retirement. Understanding this lifecycle is essential for building applications that interact with the engine, as different lifecycle stages affect visibility, search relevance, and storage costs.

The lifecycle begins with ingestion. A memory enters the system through one of several ingestion paths: direct API write, file system watcher, webhook receiver, or batch import. Regardless of the ingestion path, every memory passes through the ingestion pipeline, which performs validation, deduplication, embedding generation, and index insertion. The pipeline is designed to be idempotent: ingesting the same content twice produces the same memory record without creating duplicates. Idempotency is achieved through content-based addressing, where the memory identifier is derived from a hash of the normalized content.

After ingestion, a memory enters the active stage. Active memories are fully indexed and participate in search results. They accumulate metadata over time as the engine observes access patterns: how often the memory is retrieved, which queries it appears in, and how users interact with it (view, copy, dismiss). This metadata feeds into the relevance scoring model, allowing the engine to learn which memories are valuable for different types of queries.

The engine periodically runs a reflection process that analyzes active memories and generates insights. An insight is a new memory synthesized from patterns observed across multiple source memories. For example, if several meeting notes mention the same concern about a vendor's reliability, the reflection process might generate an insight summarizing the pattern. Insights are linked to their source memories through the lineage graph, ensuring full traceability. The reflection process runs in the background and never blocks the query path.

Memories may be updated through explicit writes or through the reflection process. Each update creates a new version of the memory while preserving the previous version in the lineage graph. The latest version is the one returned by default in search results, but clients can request historical versions for audit or comparison purposes. The version chain is bounded: after a configurable number of versions (default 50), the oldest versions are archived to cold storage and removed from the active index.

Retirement is the final lifecycle stage. A memory is retired when it is explicitly deleted by a user, when it exceeds its configured time-to-live, or when the engine determines through reflection that it has been superseded by more recent information. Retired memories are not immediately removed from the system. Instead, they are tombstoned and excluded from search results. The tombstone remains in the index for a configurable grace period (default 30 days) to ensure that all replicas have processed the deletion before the physical data is reclaimed. After the grace period, a background garbage collection process removes the tombstone and reclaims the storage space.

The lifecycle also includes a consolidation phase that runs during low-activity periods. Consolidation identifies groups of memories that cover overlapping topics and merges them into unified summaries while preserving links to the original source memories. This process reduces the total number of memories in the index without losing information, improving query performance by reducing the candidate set size. Consolidation is conservative by default: it only merges memories with a similarity score above 0.95 and identical source attribution. Operators can adjust the similarity threshold to be more or less aggressive based on their quality requirements.

Memory importance scoring evolves over the lifecycle based on access patterns and contextual signals. A newly ingested memory starts with a default importance score of 0.5. The score increases when the memory is frequently retrieved, when it is referenced by insights, or when the user explicitly marks it as important. The score decreases over time through a configurable decay function (exponential by default, with a half-life of 90 days). The importance score directly influences re-ranking: higher-importance memories receive a multiplicative boost in the final ranking, making them more likely to appear in query results. The decay function ensures that memories that are no longer relevant gradually fade from prominence without requiring explicit user intervention.

## Tenant Isolation and Multi-Tenancy

The engine supports multiple tenants within a single deployment, with strict isolation guarantees that prevent data leakage between tenants. Tenant isolation is structural, meaning it is enforced by the architecture itself rather than by application-level access checks that could be bypassed through bugs or misconfiguration.

Each tenant is assigned a unique tenant identifier at creation time. All data belonging to a tenant is prefixed with this identifier in the storage engine, creating a logical namespace that is enforced at the storage layer. The storage engine's key encoding scheme places the tenant identifier as the first component of every key, ensuring that range scans are naturally bounded to a single tenant. This design eliminates the possibility of a query accidentally crossing tenant boundaries, even in the presence of bugs in the query processing pipeline.

The vector index maintains a separate graph per tenant. While this increases memory overhead compared to a shared graph with tenant-level filtering, it provides stronger isolation guarantees and better query performance. A shared graph would require filtering during traversal, which degrades recall when the filter is highly selective (as it typically is for tenant isolation, where only one tenant's vectors are relevant). Separate graphs eliminate this degradation entirely.

Resource quotas are enforced per tenant to prevent noisy-neighbor effects. Each tenant has configurable limits for storage capacity, memory record count, query rate, and embedding computation budget. The quota enforcement layer sits between the API gateway and the engine core, rejecting requests that would exceed the tenant's limits before they consume shared resources. Quota metrics are exposed per tenant, allowing operators to monitor utilization and adjust limits proactively.

Authentication and authorization use a token-based scheme. Each API request includes a bearer token that identifies the tenant and the set of permissions granted to the caller. Tokens are validated by the API gateway before the request reaches the engine. The engine itself does not implement authentication logic; it trusts the gateway to provide a validated tenant identifier with each request. This separation of concerns simplifies the engine's security surface and concentrates authentication complexity in the gateway, where it can be tested and audited independently.

Tenant provisioning is a lightweight operation that creates the necessary storage prefixes and vector index structures. A new tenant can be provisioned in under 100 milliseconds, enabling self-service onboarding workflows. Deprovisioning is more involved: it requires draining all active queries for the tenant, deleting all storage data, deallocating the vector index, and revoking all outstanding tokens. The deprovisioning process is designed to complete within 60 seconds for tenants with up to one million memories.

Cross-tenant analytics are supported through a privileged operator API that can query aggregated metrics across all tenants without accessing individual tenant data. The analytics API provides insights into overall system utilization, tenant growth trends, and capacity planning projections. All cross-tenant queries operate on pre-aggregated data to prevent any possibility of leaking individual tenant information through query timing or result cardinality. The aggregation process runs hourly and stores results in a separate analytics store that is accessible only through the operator API.

Tenant migration between engine instances is supported for load balancing and maintenance purposes. The migration process creates a consistent snapshot of the tenant's data, transfers it to the target instance, replays any events that occurred during the transfer, and atomically switches the routing table to direct traffic to the new instance. The migration is designed to be transparent to the tenant: queries continue to be served during the migration, with a brief period (typically under one second) of elevated latency during the routing switch. The migration process validates data integrity by comparing checksums before and after the transfer, aborting if any discrepancy is detected.

The tenant lifecycle includes automated capacity monitoring that tracks each tenant's resource consumption trends and projects when they will approach their quota limits. Projections use a linear regression model fitted to the last 30 days of usage data, with seasonal adjustments for tenants that exhibit weekly or monthly patterns. When a projection indicates that a tenant will exceed a quota within 14 days, the system generates a proactive alert for the operator, allowing them to adjust quotas or discuss upgrade options with the tenant before service is impacted.

## Observability and Monitoring

Observability is a first-class concern in the engine's architecture. Every operation emits structured metrics, traces, and logs that allow operators to understand system behavior, diagnose issues, and plan capacity. The observability stack is designed to have negligible impact on the hot path, adding less than 1 microsecond of overhead per operation.

Metrics are emitted using the OpenTelemetry protocol and cover four categories: latency histograms, throughput counters, resource gauges, and error rates. Latency histograms are recorded for every stage of the query processing pipeline, every storage operation, and every vector index operation. The histograms use logarithmic bucket boundaries to provide accurate percentile estimates across a wide range of latencies (from microseconds to seconds). Throughput counters track the rate of queries, writes, compactions, and replication events. Resource gauges track memory usage, disk usage, open file descriptors, and thread pool utilization.

Distributed tracing propagates context across all internal operations. Each incoming request receives a trace identifier that follows the request through the query analysis, embedding generation, candidate retrieval, re-ranking, and response assembly stages. Child spans are created for each stage, recording the stage's start time, end time, and relevant attributes (such as the number of candidates retrieved or the number of re-ranked results). Traces are exported to the configured tracing backend (Jaeger, Zipkin, or any OpenTelemetry-compatible collector).

Structured logging uses JSON format with consistent field names across all components. Every log entry includes the timestamp, log level, component name, tenant identifier (when available), and a human-readable message. Sensitive data (memory content, query text, embedding vectors) is never included in log entries. Instead, logs reference data by identifier, allowing operators to correlate log entries with specific records when needed for debugging.

Alerting rules are defined in terms of the metrics described above. The engine ships with a set of recommended alert thresholds: query latency p99 exceeding the budget by more than 20%, error rate exceeding 1% over a 5-minute window, storage utilization exceeding 80%, and replication lag exceeding 5 seconds. These thresholds are starting points; operators should tune them based on their specific workload characteristics and SLA requirements.

Health checking is implemented through a dedicated endpoint that reports the status of all engine subsystems: storage engine (can it read and write), vector index (is it loaded and queryable), replication (is it connected and within staleness bounds), and resource limits (is memory and disk usage within safe thresholds). The health endpoint is designed for use with load balancers and orchestration systems that need to determine whether an instance should receive traffic.

Custom dashboards can be constructed using the metrics API, which provides a query language for filtering, aggregating, and transforming metric time series. The query language supports common operations including rate computation, histogram percentile extraction, label-based grouping, and arithmetic between series. For example, an operator can compute the ratio of cache hits to total queries per tenant over a 5-minute window, filtered to only include tenants with more than 100 queries in that window. The metrics API is designed for dashboard polling at 15-second intervals and includes built-in caching to prevent excessive computation for frequently requested queries.

Anomaly detection runs on top of the metrics pipeline and uses statistical methods to identify unusual behavior patterns. The detector maintains a rolling baseline for each metric using exponentially weighted moving averages and standard deviations. When a metric deviates from its baseline by more than three standard deviations for a sustained period (configurable, default 5 minutes), the detector raises an anomaly alert. This approach catches performance degradations that are too gradual for threshold-based alerts but significant enough to warrant investigation. The anomaly detector is particularly useful for detecting memory leaks (gradually increasing memory usage), index degradation (gradually increasing query latency), and workload shifts (changes in query patterns that may require configuration adjustments).

SLO (Service Level Objective) tracking provides a higher-level view of system health by measuring performance against defined targets. The engine supports configuring SLOs for query latency (e.g., 99% of queries complete within 100ms), availability (e.g., 99.9% of requests succeed), and data freshness (e.g., 99% of memories are searchable within 1 second of ingestion). SLO compliance is computed using a sliding window (default 30 days) and exposed as an error budget metric. When the error budget is exhausted, the system can automatically enable protective measures such as reducing query parallelism, rejecting low-priority background tasks, or throttling ingestion to preserve query performance.

## Security Architecture

Security in the memory engine follows a defense-in-depth approach, with multiple layers of protection that operate independently. A vulnerability in one layer does not compromise the entire system because each layer enforces its own invariants without relying on the correctness of other layers.

The outermost layer is the API gateway, which handles TLS termination, authentication, and rate limiting. All client communication uses TLS 1.3 with strong cipher suites. The gateway validates bearer tokens against the authentication service, extracts the tenant identifier and permission set, and forwards them to the engine as trusted headers. Rate limiting is applied per tenant and per endpoint, with configurable burst and sustained rate limits.

The engine's input validation layer sanitizes all data before it enters the core processing pipeline. Memory content is validated for maximum size (configurable, default 1 MB), encoding (must be valid UTF-8), and structure (frontmatter must be valid YAML if present). Query parameters are validated for type correctness, range bounds, and maximum result counts. Embedding vectors are validated for dimensionality and magnitude (NaN and infinite values are rejected). Any validation failure results in an immediate error response without touching the storage or index layers.

Data at rest is encrypted using AES-256-GCM with per-tenant encryption keys. The encryption layer sits between the storage engine and the filesystem, transparently encrypting data before it is written and decrypting it after it is read. Encryption keys are managed through an external key management service; the engine never stores raw encryption keys on disk. Key rotation is supported without downtime: new writes use the new key, while reads transparently handle data encrypted with any historical key.

Access control within the engine is capability-based. Each API token encodes a set of capabilities (read, write, admin, reflect) that determine which operations the caller can perform. Capabilities are checked at the API boundary before the request enters the processing pipeline. The capability model is designed to be minimal: most clients need only read and write capabilities, while admin capabilities (tenant management, configuration changes) are restricted to operators.

Audit logging records all security-relevant events: authentication successes and failures, authorization decisions, configuration changes, tenant provisioning and deprovisioning, and key rotation events. Audit logs are written to a separate, append-only storage path that is not accessible through the normal API. They are retained for a configurable period (default 90 days) and can be exported to external SIEM systems for centralized analysis.

Sensitive data handling follows the principle of minimal exposure. Memory content that has been marked as sensitive by the user or by automated classification is stored with additional protections: it is encrypted with a separate key, it is excluded from reflection processing, and it is scrubbed from all logs and traces. The engine uses the zeroize crate to ensure that sensitive data is cleared from memory as soon as it is no longer needed, preventing it from lingering in deallocated memory pages.

Penetration testing is conducted quarterly by an external security firm with specific expertise in database systems and AI infrastructure. The testing scope includes the API attack surface, the storage encryption implementation, the tenant isolation boundaries, and the administrative interfaces. Findings are categorized by severity (critical, high, medium, low) and tracked to resolution. Critical and high findings must be resolved before the next release; medium findings must have a remediation plan within 30 days; low findings are prioritized against the engineering backlog. All historical penetration test reports are maintained in the security documentation repository with restricted access.

The engine implements defense against inference attacks that attempt to extract information about one tenant's data by observing the system's behavior when processing queries for another tenant. Timing-based inference attacks are mitigated by adding constant-time padding to all operations that depend on tenant data size, ensuring that query response times do not leak information about the number of memories a tenant has. Cache-based inference attacks are mitigated by partitioning all caches by tenant, preventing one tenant's queries from evicting another tenant's cache entries and observing the resulting latency changes.

Compliance features support regulatory requirements including GDPR, SOC 2, and HIPAA. The engine provides data residency controls that restrict where a tenant's data is stored geographically, right-to-erasure support that permanently and verifiably deletes all data associated with an identifier, and data processing audit trails that record every operation performed on tenant data. The compliance module generates automated reports that summarize data processing activities over a configurable period, formatted for submission to regulatory authorities or inclusion in compliance audits.

## Embedding Model Integration

The embedding model integration layer provides a clean abstraction over the neural network models used to convert text into vector representations. This abstraction allows the engine to support multiple model providers and model versions without changing the core indexing or query logic. Model selection is configured per tenant, enabling different tenants to use different models based on their language, domain, or accuracy requirements.

The integration layer defines a trait that all model implementations must satisfy. The trait requires three methods: embed_single (convert one text into one vector), embed_batch (convert multiple texts into multiple vectors), and dimensionality (return the output vector size). The trait is designed to be minimal and implementation-agnostic, supporting both local models (loaded into the engine process) and remote models (accessed through HTTP or gRPC APIs).

Local model execution uses the ONNX Runtime as the inference backend. Models are loaded from ONNX format files at startup and cached in memory for the lifetime of the process. The runtime supports CPU execution with threading (default: number of physical cores) and optional GPU acceleration through CUDA or CoreML providers. Tokenization is performed using the model's bundled tokenizer configuration, which handles vocabulary lookup, subword splitting, and padding to the model's maximum sequence length.

Remote model execution sends text to an external embedding service and receives vectors in response. The integration layer implements connection pooling, request batching, timeout handling, and retry logic with exponential backoff. When the remote service is unavailable, the engine can optionally fall back to a local model (if configured) to maintain availability at the cost of potentially different embeddings. The fallback behavior is logged and surfaced as a metric so operators can monitor its frequency.

Model versioning is handled through a registry that maps model identifiers to their configurations. When a tenant changes their model configuration, new memories are embedded with the new model while existing memories retain their original embeddings. The engine supports a background re-embedding process that incrementally re-computes embeddings for existing memories using the new model. This process is rate-limited to avoid overwhelming the embedding compute budget and is designed to complete within a bounded time (proportional to the number of memories and the embedding throughput).

The embedding cache reduces redundant computation by storing recently generated embeddings in an LRU cache keyed by content hash. When the same content is ingested multiple times (which occurs frequently during re-ingestion and synchronization workflows), the cache provides the embedding without invoking the model. The cache size is configurable per tenant and defaults to 10,000 entries, which covers the typical working set for interactive usage patterns.

Embedding quality monitoring runs continuously in the background. The monitor samples pairs of memories that are known to be semantically similar (based on shared links, co-retrieval patterns, or explicit user annotations) and verifies that their embedding similarity exceeds a minimum threshold. If the monitor detects a degradation in embedding quality (for example, due to a model update that changes the embedding space), it raises an alert and optionally triggers a re-embedding process. This closed-loop monitoring ensures that the vector index maintains its retrieval quality over time.

Embedding drift monitoring addresses a subtle but important failure mode in production systems. Over time, the distribution of text ingested into the system may shift away from the distribution the embedding model was trained on. This drift causes gradual degradation in retrieval quality that is difficult to detect through standard metrics because it manifests as slowly declining relevance rather than an abrupt failure. The drift monitor maintains a reference distribution of embedding vectors computed from a curated evaluation set and periodically compares the distribution of newly generated embeddings against this reference. The comparison uses maximum mean discrepancy, a statistical measure that quantifies the difference between two distributions in the embedding space. When the drift exceeds a configurable threshold, the monitor alerts operators and recommends either fine-tuning the current model on recent data or switching to a newer model that better represents the current distribution.

The embedding pipeline supports content-aware chunking for long documents that exceed the model's maximum sequence length. Rather than truncating the input (which loses information from the end of the document) or splitting at fixed character boundaries (which can break semantic units), the chunker identifies natural break points such as paragraph boundaries, section headings, and sentence endings. Each chunk is embedded independently, and the resulting vectors are stored with metadata linking them back to their source document and position within it. During query time, chunk-level results are aggregated to produce document-level rankings using a configurable aggregation strategy (max similarity, mean similarity, or a weighted combination that favors the best-matching chunk).

Model evaluation and comparison are supported through an A/B testing framework that allows operators to run two embedding models simultaneously and compare their retrieval quality. The framework splits incoming queries between the two models, retrieves results independently, and collects implicit feedback signals (click-through rates, dwell times, explicit relevance ratings) to determine which model produces better results. The comparison runs for a configurable period (default 7 days) and produces a statistical significance report. If the new model is significantly better, the operator can switch all traffic to it with a single configuration change.

## Compaction, Space Reclamation, and Operational Tuning

Compaction is the background process that maintains the storage engine's efficiency over time. Without compaction, the storage engine would accumulate an unbounded number of sorted string tables, degrading read performance (because more tables must be checked per read) and wasting disk space (because deleted and overwritten entries persist in older tables). Compaction merges tables, resolves superseded entries, and organizes data into a structure that optimizes read performance.

The engine uses a leveled compaction strategy with six levels (L0 through L5). Each level has a target size that is ten times the target size of the level above it. L0 has a target of 64 MB (matching the memtable size), L1 has a target of 640 MB, and so on up to L5 with a target of approximately 6.4 TB. When a level exceeds its target size, the compaction scheduler selects one or more tables from that level, merges them with overlapping tables in the next level, and writes the result as new tables in the next level. The old tables are marked for deletion after the merge completes.

Compaction scheduling uses a priority-based algorithm that balances read performance, write amplification, and space amplification. The scheduler assigns a priority score to each potential compaction task based on the level's current size relative to its target (levels that are more over-target get higher priority), the estimated write amplification of the compaction (merges that produce less write amplification get higher priority), and the age of the oldest unmerged data in the level (older data gets higher priority to ensure timely garbage collection).

The compaction process is rate-limited to prevent it from consuming excessive I/O bandwidth and interfering with foreground operations. The rate limit is configurable and defaults to 100 MB per second of write bandwidth dedicated to compaction. Under heavy write load, compaction may fall behind temporarily, causing the number of L0 tables to grow. When the L0 table count exceeds a configured threshold (default 12), the engine begins throttling incoming writes to give compaction time to catch up. This backpressure mechanism prevents the system from entering a state where read performance degrades unboundedly due to excessive L0 table accumulation.

Space reclamation for deleted memories involves two phases. In the first phase, the memory is tombstoned in the storage engine by writing a deletion marker. The tombstone is a small record that indicates the key has been deleted. Reads that encounter a tombstone return "not found" without consulting older tables. In the second phase, compaction processes tables containing tombstones, physically removing the deleted entries and their tombstones from the merged output. Tombstones must persist until compaction has processed all tables that might contain the deleted key, which is guaranteed once the tombstone has been compacted into the deepest level.

Compaction metrics track the health and efficiency of the process. Key metrics include the compaction throughput (bytes per second), the current size of each level relative to its target, the write amplification ratio (compaction bytes written divided by application bytes written), the space amplification ratio (physical disk usage divided by logical data size), and the estimated time to complete all pending compactions. These metrics are critical for capacity planning: a sustained write amplification above 20x or space amplification above 2x indicates that the compaction configuration should be tuned.

The compaction process also handles the physical removal of vector index entries. When a memory is tombstoned, its vector must be removed from the HNSW graph. Graph deletions are more expensive than storage deletions because they require reconnecting the deleted node's neighbors to maintain graph connectivity. The engine batches graph deletions and processes them during a dedicated compaction phase to minimize the impact on query latency. The batch size is bounded (default 1000 deletions per batch) to keep the compaction phase duration predictable.

Compaction parallelism controls how many compaction tasks can execute simultaneously. The default is two concurrent compaction tasks, which balances compaction throughput against I/O contention with foreground operations. Increasing parallelism speeds up compaction at the cost of higher I/O utilization, which can increase query tail latency. The engine monitors the impact of compaction on query latency and automatically reduces parallelism if query p99 latency exceeds its budget by more than 10%, resuming full parallelism when latency returns to normal.

The compaction scheduler also considers thermal throttling on storage devices. Modern SSDs reduce their write throughput when their internal temperature exceeds a threshold, which can cause compaction to slow down unexpectedly. The engine monitors storage device temperature through the SMART interface and proactively reduces compaction rate when the temperature approaches the throttling threshold. This prevents the cascading failure mode where thermal throttling causes compaction to fall behind, which causes L0 table accumulation, which triggers write throttling, which causes application-visible latency spikes.

Beyond compaction, the engine exposes a comprehensive set of configuration parameters that allow operators to tune its behavior for their specific workload and hardware. Configuration is specified through a TOML file that is read at startup. Changes to most parameters require a restart; a small subset of parameters (query timeouts, rate limits, log levels) can be changed at runtime through the admin API.

Storage configuration controls the memtable size, WAL sync mode, compaction rate limit, level size targets, and bloom filter false positive rate. The memtable size is the most impactful parameter for write throughput: larger memtables reduce the frequency of flushes and L0 compactions, but increase memory usage and recovery time after a crash (because a larger WAL must be replayed). The recommended memtable size is 64 MB for general workloads, 256 MB for write-heavy workloads, and 16 MB for memory-constrained deployments.

Vector index configuration controls the HNSW parameters: M (connections per node), ef_construction (search width during insertion), and ef_search (search width during queries). Increasing M improves recall but increases memory usage linearly. Increasing ef_construction improves graph quality but increases insertion time. Increasing ef_search improves query recall but increases query latency. The recommended starting point is M=16, ef_construction=200, ef_search=128, which provides approximately 95% recall at 10-millisecond query latency for 768-dimensional vectors.

Query configuration controls the default result count, maximum result count, re-ranking model weights, and per-stage latency budgets. Latency budgets are enforced through timeouts: if a stage exceeds its budget, it returns the best results available within the time limit rather than blocking indefinitely. This degraded-but-responsive behavior is preferable to timeout errors in most applications. The budgets are: query analysis 5 ms, embedding generation 10 ms, candidate retrieval 10 ms, re-ranking 20 ms, response assembly 20 ms, for a total budget of 65 ms with 35 ms of headroom for the 100 ms end-to-end target.

Replication configuration controls the event log connection, replication lag alarm threshold, and conflict resolution strategy. For single-instance deployments, replication is disabled by default. For multi-instance deployments, the operator must configure the event log endpoint and the instance identifier. The engine validates the replication configuration at startup and refuses to start if the event log is unreachable, preventing split-brain scenarios where an instance operates independently and diverges from the cluster.

Resource limit configuration controls the per-tenant quotas and the global resource caps. Global caps include maximum memory usage (default: 80% of available RAM), maximum disk usage (default: 90% of available disk), and maximum thread count (default: 2x physical cores). Per-tenant quotas are configured through the admin API and stored in the engine's metadata store. The quota enforcement layer checks limits before every resource-consuming operation and returns a capacity error if the limit would be exceeded.

Logging and tracing configuration controls the log level, log format, trace sampling rate, and export endpoints. The default log level is "info" for production deployments and "debug" for development. Trace sampling uses a probabilistic sampler that exports a configurable fraction of traces (default: 1% for production, 100% for development). Operators can also configure per-tenant trace sampling rates for targeted debugging without increasing the overall trace volume.

The engine ships with a configuration validation tool that checks a TOML file for errors, warns about suboptimal settings, and suggests adjustments based on the deployment's hardware profile. The validator reports issues in three categories: errors (configuration that will prevent startup), warnings (configuration that will degrade performance), and suggestions (configuration that could be improved based on best practices). Running the validator before deploying configuration changes catches common mistakes such as setting the memtable size larger than available memory or configuring latency budgets that sum to more than the end-to-end target.

Configuration profiles provide pre-tuned parameter sets for common deployment scenarios. The "write-heavy" profile increases the memtable size to 256 MB, raises the compaction rate limit to 200 MB per second, and reduces ef_search to 64 for faster queries at the cost of slightly lower recall. The "read-optimized" profile reduces the memtable size to 32 MB (keeping more memory available for block cache), increases ef_search to 256 for maximum recall, and enables aggressive bloom filter compression to reduce memory overhead. The "balanced" profile uses the default parameters and is suitable for workloads with roughly equal read and write volumes. Operators can start with a profile and override individual parameters as needed based on their monitoring data.

Hot configuration reloading is supported for a subset of parameters that do not require structural changes to the engine's internal state. These include query timeouts, rate limits, log levels, tenant quotas, and replication lag alarm thresholds. When a configuration change is submitted through the admin API, the engine validates the new values against the same rules used during startup validation, applies them atomically to all active components, and emits a configuration change event to the audit log. Parameters that require a restart (such as memtable size, HNSW M, and encryption settings) are rejected by the hot reload API with an error message indicating that a restart is needed.

The engine also supports configuration drift detection for multi-instance deployments. Each instance periodically broadcasts its active configuration to the cluster metadata store. A background process compares configurations across all instances and alerts the operator if any instance has drifted from the cluster's expected configuration. This catches scenarios where an operator updates the configuration on some instances but forgets others, which can cause subtle behavioral differences that are difficult to diagnose.

Capacity planning tools are built into the engine's admin interface. Given a tenant's current data size, growth rate, query volume, and retention policy, the capacity planner estimates the required compute, memory, storage, and network resources for the next 6 and 12 months. The estimates account for compaction overhead, replication overhead, and the memory requirements of the vector index. The planner generates a human-readable report that can be shared with infrastructure teams for procurement and provisioning decisions.
